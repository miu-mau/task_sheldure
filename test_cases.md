# Тест-кейсы для планировщика задач

## Тест-кейс 1: Создание задачи и автоматическое планирование по времени

**Цель:** Проверить создание задачи через gRPC API и автоматическое перемещение задачи из статуса DRAFT в QUEUED при наступлении времени scheduled_at.

**Предусловия:**
- Запущен сервис планировщика (`go run ./cmd/app`)
- Запущена БД и выполнены миграции
- Запущен Kafka

**Шаги:**
1. Создать задачу через CLI с текущим временем scheduled_at:
   ```bash
   go run ./cmd/cli -cmd create "test task 1"
   ```
2. Получить ID созданной задачи из ответа
3. Проверить статус задачи через `GetTask` - должен быть `TASK_STATUS_DRAFT`
4. Подождать 5-10 секунд (время тикера планировщика)
5. Повторно проверить статус задачи - должен быть `TASK_STATUS_QUEUED`

**Ожидаемый результат:**
- Задача успешно создана со статусом DRAFT
- Через несколько секунд статус автоматически меняется на QUEUED
- Задача появляется в Kafka топике `tasks`

**Критерии приемки:**
- Задача создана в БД
- Статус изменяется с DRAFT на QUEUED
- Сообщение отправлено в Kafka

## Тест-кейс 2: Назначение задачи конкретному воркеру

**Цель:** Проверить, что задача с указанным worker_id отправляется в специализированный топик для этого воркера.

**Предусловия:**
- Запущен сервис планировщика
- Запущен воркер с ID `worker1`
- Запущен Kafka

**Шаги:**
1. Создать задачу для конкретного воркера:
   ```bash
   go run ./cmd/cli -cmd create "task for worker1" -worker-id worker1
   ```
2. Получить ID задачи
3. Подождать 5-10 секунд
4. Проверить статус задачи - должен быть `TASK_STATUS_QUEUED`
5. Проверить, что сообщение появилось в топике `tasks-worker-worker1` (а не в общем топике `tasks`)

**Ожидаемый результат:**
- Задача создана с указанным worker_id
- Задача отправлена в топик `tasks-worker-worker1`
- Воркер worker1 получает и обрабатывает задачу
- Задача не попадает в общий топик `tasks`

**Критерии приемки:**
- Задача в БД имеет поле worker_id = "worker1"
- Сообщение в Kafka отправлено в правильный топик
- Воркер worker1 получает задачу

## Тест-кейс 3: Обработка задачи воркером и изменение статуса

**Цель:** Проверить полный цикл выполнения задачи: QUEUED → RUNNING → SUCCESS.

**Предусловия:**
- Запущен сервис планировщика
- Запущен воркер (`go run ./cmd/worker`)
- Запущен Kafka

**Шаги:**
1. Создать задачу:
   ```bash
   go run ./cmd/cli -cmd create "task to execute"
   ```
2. Получить ID задачи
3. Подождать, пока задача перейдет в статус QUEUED
4. Проверить статус задачи - должен быть `TASK_STATUS_RUNNING` (воркер начал обработку)
5. Подождать завершения выполнения (воркер выполняет задачу ~100ms)
6. Проверить финальный статус задачи - должен быть `TASK_STATUS_SUCCESS`

**Ожидаемый результат:**
- Задача проходит через статусы: DRAFT → QUEUED → RUNNING → SUCCESS
- Воркер успешно обрабатывает задачу
- Создается запись Attempt с статусом SUCCESS
- Время выполнения зафиксировано

**Критерии приемки:**
- Все статусы изменяются последовательно
- Attempt создан и имеет статус ATTEMPT_STATUS_SUCCESS
- Задача завершена успешно

## Тест-кейс 4: Приоритизация задач при планировании

**Цель:** Проверить, что задачи с более высоким приоритетом обрабатываются раньше задач с низким приоритетом.

**Предусловия:**
- Запущен сервис планировщика
- Запущен Kafka

**Шаги:**
1. Создать задачу с низким приоритетом (priority = 1) через gRPC API
2. Создать задачу с высоким приоритетом (priority = 10) через gRPC API
3. Обе задачи должны иметь одинаковое scheduled_at (текущее время)
4. Подождать 5-10 секунд
5. Проверить порядок появления задач в Kafka топике

**Ожидаемый результат:**
- Задача с priority = 10 отправляется в очередь раньше задачи с priority = 1
- Порядок обработки соответствует приоритету
- В БД задачи отсортированы по приоритету (DESC) и времени scheduled_at (ASC)

**Критерии приемки:**
- Задача с высоким приоритетом обрабатывается первой
- SQL запрос GetReadyTasks сортирует по priority DESC, scheduled_at ASC

## Тест-кейс 5: Отмена задачи и обработка ошибок

**Цель:** Проверить отмену задачи и обработку ошибок при выполнении.

**Предусловия:**
- Запущен сервис планировщика
- Запущен воркер
- Запущен Kafka

**Шаги:**
1. Создать задачу:
   ```bash
   go run ./cmd/cli -cmd create "task to cancel"
   ```
2. Получить ID задачи
3. Отменить задачу через gRPC метод `CancelTask` до того, как она будет обработана
4. Проверить статус задачи - должен быть `TASK_STATUS_CANCELLED`
5. Создать другую задачу и дождаться, пока она попадет в очередь
6. Симулировать ошибку выполнения в воркере (если возможно) или проверить обработку ошибок через метод `ReportAttempt` с статусом FAILED
7. Проверить статус задачи - должен быть `TASK_STATUS_FAILED`
8. Проверить, что поле last_error заполнено

**Ожидаемый результат:**
- Задача успешно отменяется и получает статус CANCELLED
- При ошибке выполнения задача получает статус FAILED
- Поле last_error содержит описание ошибки
- Создается Attempt с статусом ATTEMPT_STATUS_FAILED

**Критерии приемки:**
- Отмена задачи работает корректно
- Ошибки обрабатываются и сохраняются
- Статусы изменяются правильно
- Attempt создается с правильным статусом
